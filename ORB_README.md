# orb_robot — стратегия ORB (Opening Range Breakout), Si M15

Робот на пробой утреннего диапазона (10:00-11:00 МСК), с календарным фильтром
(`event_calendar.py`/`orb_calendar.py`), риск-модулем (`orb_risk.py`) и тремя
режимами работы: `backtest` (история MOEX ISS), `paper` (живые данные QUIK, без
реальных заявок) и `live` (реальные заявки).

## Файлы

```
orb_strategy.py     — чистая логика ORB (диапазон/вход/стоп/EOD), без QuikPy/pandas
orb_calendar.py      — блокировки входа + принудительное закрытие + ролловер контракта
orb_risk.py          — размер позиции, дневной/недельный лимит, kill switch
orb_journal.py       — CSV-журнал сделок/пропусков + дневная сводка
orb_data_moex.py      — загрузка M15 (агрегация из 1-мин) с MOEX ISS + parquet-кэш
orb_backtest.py       — движок бэктеста (склейка контрактов, комиссия/slippage)
orb_broker_quik.py    — отправка заявок через QuikPy (ТРЕБУЕТ проверки перед live!)
orb_account.py         — READ-ONLY чтение средств счёта FORTS
orb_robot.py          — точка входа (консоль): backtest / paper / live
orb_window.py          — окно (Tkinter): Робот/Лог/Настройки/Бэктест/Аналитика/Счёт
config_orb.yaml        — конфиг
event_calendar.py, cbr_dates.csv — календарь ЦБ/CPI/клиринг/экспирация
run_orb_window.bat, run_orb_backtest.bat, run_orb_paper.bat, run_orb_live.bat — запуск на Windows
tests/test_orb_*.py    — pytest
```

## Окно (GUI)

`python orb_window.py` (на Windows — `run_orb_window.bat`) открывает окно с вкладками:

- **Робот** — контракт/график/ТФ и лента входов/выходов/пропусков в реальном времени;
- **Лог** — полный технический лог (то же, что и в консоли/`logs/orb_robot.log`);
- **Настройки** — режим (paper/live), депозит, тег графика, ACCOUNT/CLIENT_CODE,
  риск-модуль (`risk:`) и переключатели поведения стратегии (`strategy:`) — те же
  поля, что в `config_orb.yaml`, сохраняются туда же (кнопка «Сохранить»);
  включение live требует подтверждения в диалоговом окне;
- **Бэктест (MOEX ISS)** — кнопка «Запустить бэктест» на параметрах из
  `config_orb.yaml: backtest`, результат (сделки/winrate/PF/PnL) выводится тут же,
  без блокировки интерфейса;
- **Бэктест (QUIK)** — тот же прогон стратегии, но на свечах уже открытого в QUIK
  M15-графика (chart_tag), один текущий контракт и столько истории, сколько
  реально загружено в терминале — без похода в сеть. Без комиссии и
  проскальзывания (просто «прогнать по тому, что вижу на графике»); ГО и
  стоимость пункта читаются вживую из QUIK (текущие значения, не исторические на
  момент каждой сделки). Требует отдельного подключения к терминалу, поэтому
  недоступен, пока робот запущен из окна (Старт/Стоп), и наоборот;

  Оба бэктеста (и из окна, и консольный `--mode backtest`) сохраняют статистику:
  - `logs/orb_backtest_trades.csv` — каждая сделка ПОСЛЕДНЕГО прогона
    (перезаписывается при каждом запуске бэктеста — для разбора в Excel);
  - `logs/orb_backtest_runs.csv` — история прогонов, по строке на запуск
    (накапливается): дата/время, источник (moex_iss/quik_chart), период, все
    параметры (депозит, комиссия/слиппедж, риск-настройки, allow_position_flip,
    expiration_zone_mode) и итог (сделки/winrate/PF/PnL/пропуски, суммы
    прибыльных/убыточных сделок, итог за период в % от депозита, среднее
    за месяц в ₽ и %) — чтобы сравнивать результаты при разных настройках,
    не переписывая цифры вручную. Если формат колонок менялся (после
    обновления кода) — старый файл автоматически откладывается в `.bak`;

  В вывод бэктеста (вкладка/консоль) дополнительно печатается расширенная
  статистика: суммы прибыльных и убыточных сделок, итог за период (₽ и % от
  депозита), среднее за месяц (₽ и %) и помесячная разбивка PnL. Проценты —
  от стартового депозита (он фиксированный, без реинвестирования); месяцы —
  календарная длина периода (месяц без сделок тоже в знаменателе);
- **Аналитика** — сводка по `logs/orb_trades.csv`/`logs/orb_skips.csv`, обновляется
  автоматически при каждой новой сделке (и по кнопке «Обновить»);
- **Счёт** — средства счёта FORTS (`orb_account.py`), опрашивается каждые
  `account_poll_seconds` секунд, пока робот запущен из окна (Старт/Стоп).

Кнопки Старт/Стоп в шапке запускают тот же `run_paper_or_live`, что и консольный
`orb_robot.py --mode paper/live` — окно лишь подписывается на события через очередь
(поток движка отдельно от потока интерфейса), заявки в paper по-прежнему не шлются.

## Схема режимов

```
              ┌──────────────┐
              │ config_orb.yaml│  mode: backtest|paper|live
              └──────┬────────┘
                     │
        ┌────────────┼─────────────┐
        ▼            ▼             ▼
   backtest        paper          live
   MOEX ISS    QUIK/QuikPy    QUIK/QuikPy
   (сеть,       (живые бары,   (живые бары +
   без QUIK)    без заявок)    РЕАЛЬНЫЕ заявки)
        │            │             │
        └─────┬──────┴──────┬──────┘
              ▼             ▼
        orb_strategy.py (одна и та же логика везде)
        orb_calendar.py + orb_risk.py (одни и те же лимиты везде)
              │
              ▼
        orb_journal.py (CSV: trades.csv, skips.csv)
```

Все три режима используют РОВНО одну и ту же торговую логику
(`orb_strategy.process_bar`) и одни и те же календарные/риск-проверки —
отличается только источник баров и то, отправляются ли реальные заявки.

## Как это работает (кратко)

1. **Диапазон** 10:00:00-10:59:59 МСК — high/low по 4 барам M15.
2. **Вход** 11:00-18:40: первое закрытие выше диапазона — лонг, ниже — шорт.
   Максимум один лонг и один шорт в день; позиция всегда одна (нетто).
3. **Стоп** — противоположная граница диапазона, без тейка и трейлинга.
4. **18:40** — принудительное закрытие по рынку (безусловно).
5. **Календарь**: жёсткий блок — день ЦБ 13:00-15:30 (входы блокированы, открытая
   позиция закрывается принудительно); мягкий блок — среда 18:45-19:30, клиринг
   14:00-14:05/18:50-19:05; зона ±2 торговых дня от экспирации — входы блокированы,
   контракт переключается на следующий квартальный.
6. **Риск**: размер позиции = min(риск-лимит, ГО-лимит) с округлением вниз;
   слишком широкий диапазон (> `max_stop_pt`) — сигнал дня пропускается; дневной
   лимит убытка останавливает вход до конца дня; недельный аварийный лимит
   переводит робота в `halt` (нужен ручной сброс); файл `STOP` в рабочей папке —
   немедленная остановка.

## Бэктест

```
python orb_robot.py --mode backtest
```

На Windows — то же самое через `run_orb_backtest.bat`.

Данные — MOEX ISS (`iss.moex.com`, бесплатно, без ключа), 1-минутные свечи
агрегируются в M15 через pandas и кэшируются в parquet (`backtest.cache_dir` в
конфиге). Повторный прогон на том же периоде не ходит в сеть.

Склейка контрактов — БЕЗ бэк-адъюстмента: для каждого дня берётся реальный OHLC
того квартального контракта, который в этот день активен по правилу ролловера
(`orb_calendar.active_contract`, переход за 2 торговых дня до экспирации). Гэпов
на стыке нет в принципе (в отличие от классической непрерывной серии), плюс
зона экспирации и так блокирует входы, а позиция всегда закрывается день в день.

Упрощения бэктеста (осознанные):
- депозит фиксирован на весь период (без начисления сложного процента на equity);
- ГО на контракт — постоянное предположение из конфига (`go_per_contract_assumed`),
  в реальности плавает и зависит от биржи/брокера; в paper/live вместо этого
  читается живое ГО из QUIK (`BUYDEPO`/`SELLDEPO`);
- комиссия и проскальзывание — по конфигу, на обе стороны сделки.

### Результат проверочного прогона (2025-07-11 — 2026-07-10)

`python orb_robot.py --mode backtest` (депозит 300 000 ₽, комиссия 5 ₽/контракт,
проскальзывание 2 тика, `max_stop_pt=600`):

| Метрика | Наш бэктест (MOEX ISS) | Ориентир (TradingView) |
|---|---|---|
| Сделок | 169 | ~250 |
| Winrate | 57.4% | ~55% |
| Профит-фактор | 1.79 | ~1.5 |
| Средний PnL **на контракт** | ~+85 ₽ | ~+70 ₽ |

Средний PnL на сделку у нас +484 ₽ — это НЕ то же самое, что «на контракт» из
эталона: размер позиции динамический (риск-модуль, в среднем ~5.7 контракта на
сделку), поэтому для сравнения PnL нормирован делением на qty (`sum(pnl_rub) /
sum(qty)` = 84.4 ₽/контракт, среднее по сделкам — 87.0 ₽/контракт). Winrate и
профит-фактор от размера позиции не зависят и сравнимы напрямую.

Число сделок (169 против ~250) — того же порядка, разница объясняется другим
источником данных и, в основном, фильтром `max_stop_pt`: 145 из 361 сигналов
дня были пропущены как «диапазон шире 600 пунктов» (структурная особенность
Si в этот период, а не баг фильтра — см. разбивку пропусков ниже). Winrate,
профит-фактор и PnL/контракт достаточно близки к ориентиру, чтобы не подозревать
ошибку в логике — расхождение не «в разы», а в пределах ожидаемого от разницы
источника данных и модели исполнения.

Пропуски сигналов за период: `range_too_wide=145, blocked_expiration_adj=30,
already_traded=10, blocked_clearing=4, blocked_cbr=2`. Выходы: `eod=138 (82%),
stop=29 (17%), cbr_flat=2` — большинство дней закрывается по времени (18:40),
что для ORB без тейка ожидаемо.

### Сверка с эталонным Pine-скриптом (si_strategy_lab.pine)

По исходному Pine-скрипту, которым писали спецификацию, нашлись два места, где
его РЕАЛЬНОЕ поведение отличается от того, что написано текстом промпта —
оба вынесены в `config_orb.yaml` → `strategy:` как переключатели:

- **`allow_position_flip`** (по умолчанию `false`) — в Pine условия входа
  (`strategy.position_size <= 0` для лонга, `>= 0` для шорта) технически
  позволяют развернуть позицию противоположным сигналом, а не игнорировать его,
  как написано в спецификации («позиция всегда одна»). Проверили эмпирически:
  **на факт результат не влияет вообще** (169 сделок что с `false`, что с
  `true`) — стоп позиции всегда равен ПРОТИВОПОЛОЖНОЙ границе диапазона, то
  есть ровно тому же уровню, что и порог для входа с другой стороны, поэтому
  проверка стопа всегда срабатывает раньше проверки на разворот (см. тест
  `test_allow_flip_reverses_position_on_opposite_breakout` в
  `tests/test_orb_strategy.py` — разворот там достижим только пока стоп не
  задет, что для ORB структурно совпадает с моментом входа). Флаг оставлен для
  прозрачности и на случай будущих модификаций стратегии, где стоп и порог
  входа разъедутся.
- **`expiration_zone_mode`** (по умолчанию `trading_days`) — Pine считает зону
  вокруг экспирации наивно, `±2 календарных дня` по номеру дня месяца; наш
  `event_calendar.EXPIRATION_ADJ` — честные `±2 торговых дня` (через выходные
  зона расширяется, т.к. экспирация всегда четверг, и захватывает следующий
  понедельник). На проверочном периоде разница — 169 → 171 сделка (`calendar_days`
  снимает блокировку с 2 из 4 «лишних» понедельников), PnL/контракт сдвигается
  84 → 91 ₽ — то есть **не приближает** к ориентиру ~70 ₽, а слегка отдаляет;
  на выборке 169-171 сделок это шум, а не значимый эффект.

Итог сверки: ни один из двух найденных отличий сам по себе не объясняет разрыв
в числе сделок (169-171 против ~250 в эталоне). Более вероятная причина —
разный таймфрейм: заголовок Pine-файла — «единый каркас… на Si (M5)», и одна
из четырёх стратегий в нём (Post-Clearing, `hm==1405`) физически требует
M5-графика; неизвестно, на каком именно ТФ гоняли ORB для эталонных цифр. На
M5 диапазон/пробой считаются точнее (по 5-минутным барам вместо 15-минутных),
что естественно даёт больше сделок. Спецификация ORB для нашего робота явно
требует M15 — менять это без явного запроса не стал.

## Чек-лист запуска paper

1. Открыть в QUIK график Si M15 с тегом `chart_tag` из конфига (по умолчанию `si15m`).
2. Проверить в логе строку «Ожидаемый активный контракт на сегодня: SiXN» —
   убедиться, что график привязан именно к этому контракту (робот сам график
   не переключает — это делает MOEX ISS для бэктеста, но для paper/live нужен
   открытый график нужного контракта вручную).
3. `slot` в `config_orb.yaml` — порт QuikPy (по умолчанию 34142/34143); если
   параллельно запускаете что-то ещё через QuikPy на этом же терминале —
   держите разные порты у каждого процесса.
4. `mode: paper`, `live_trading: false` — заявки не отправляются, только
   `logs/orb_trades.csv`, `logs/orb_skips.csv` и лог.
5. Если робот запущен не с самого начала дня — в логе будет предупреждение,
   если по разметке уже должна быть открытая позиция; сверь вручную с реальным
   состоянием счёта в QUIK (авто-сверки открытых позиций при рестарте нет).
6. `python orb_robot.py --mode paper` (на Windows — `run_orb_paper.bat`), или
   `orb_window.py`/`run_orb_window.bat` — там же вкладка «Счёт» и лента сигналов.

## Чек-лист перехода на live

1. Сначала — минимум несколько дней paper без сюрпризов (сверяй
   `logs/orb_trades.csv`/`logs/orb_skips.csv` с тем, что видно на графике).
2. **Обязательно проверить `orb_broker_quik.py`** против СВОЕЙ версии QuikPy:
   формат транзакции (`ACTION`/`OPERATION`/`TRANS_ID`/...) стандартный для
   QUIK/QLUA, но не тестировался против реального терминала в этой среде
   (QUIK — Windows-only, здесь недоступен). Проверь на 1 контракте вручную.
3. Заполнить `account` (и `client_code`, если нужен брокеру) в `config_orb.yaml`.
4. Убедиться, что стоп выставляется НАСТОЯЩЕЙ стоп-заявкой в терминале
   (`send_stop_order`) — если робот упадёт, позиция должна остаться защищённой
   биржевым стопом, а не программной проверкой.
5. Выставить `live_trading: true` и `mode: live` (или сделать это на вкладке
   «Настройки» в `orb_window.py` — там же диалог-подтверждение вместо ввода в консоли).
6. Запустить `python orb_robot.py --mode live` (на Windows — `run_orb_live.bat`) —
   потребует ввода `yes` в консоли для подтверждения перед стартом; из окна —
   кнопка «Старт» на вкладке «Настройки» с выбранным режимом live и диалог-подтверждение.
7. Знать, где лежит kill switch: создать пустой файл `STOP` в рабочей папке
   (`kill_switch_dir` в конфиге) немедленно останавливает робота и закрывает
   позицию по рынку.
8. Помнить про недельный halt: если недельный убыток достиг
   `risk.weekly_halt_limit` — робот перестаёт входить в рынок и требует
   ручного сброса (`orb_risk.reset_halt`, редактированием
   `logs/orb_risk_state.json` или отдельным скриптом).

## Сверка исполнения заявок (execution.verify)

В live робот не полагается на «отправил и забыл»: после каждой заявки он читает
ФАКТИЧЕСКУЮ позицию из QUIK (`get_futures_holding` → `totalnet`, см.
`orb_account.read_position`) и действует по факту. Управляется секцией
`execution` в `config_orb.yaml` (`verify: true` по умолчанию):

- **вход** — подтверждается фактический фил; при частичном филе размер стопа и
  журнала приводится к факту; если позиция не открылась (net=0) — внутреннее
  состояние сбрасывается в плоское + алерт (без этого робот позже пытался бы
  «закрыть» несуществующую позицию и открыл бы противоположную);
- **стоп** — если стоп-заявка не принята, повтор; если и повтор не прошёл —
  аварийное закрытие позиции (голую позицию без защиты не держим);
- **закрытие (EOD/ЦБ/стоп/kill)** — сначала снимается висящая GTC-стоп-заявка
  (иначе осталась бы активной и могла сработать на следующий день), затем
  читается реальная позиция и закрывается ровно она. Это чинит **двойное
  исполнение** на выходе по `stop` (брокерский стоп мог уже закрыть позицию — в
  этом случае рыночное закрытие НЕ шлётся). Если после `close_retries` попыток
  позиция не ушла в ноль — критический алерт «закрой вручную».

Если у твоей версии QuikPy нет `get_futures_holding`/`get_stop_orders` — сверка
деградирует до старого поведения (заявки вслепую) с предупреждением в логе; тогда
проверь имена методов и поправь `orb_account.read_position`/`active_stop_orders`.

## Охрана графика (chart_guard)

Робот берёт сигналы из графика по `chart_tag`, а торгует контракт, который
вычисляет сам (`active_contract`). Если график привязан не к тому контракту
(забыли переключить после ролловера, открыт чужой инструмент) — сигналы и заявки
разъезжаются молча. Охрана (секция `chart_guard`, `enabled: true` по умолчанию)
ловит это тремя проверками по убыванию точности:

1. **точное имя sec за тегом** — если QuikPy умеет отдать код инструмента графика
   (`orb_robot.chart_sec`); на старте робот пишет в лог, доступен ли этот метод на
   твоей версии QuikPy;
2. **сверка цены** — |последний close графика − LAST торгуемого контракта| /
   LAST выше `price_tolerance_pct` (по умолчанию 1%; спред между соседними
   квартальными Si обычно 3–4% carry, так что порог их различает, а внутрибарный
   дрейф — нет);
3. **свежесть бара** — последний бар графика старше `max_bar_age_minutes`
   (истёкший/замерший контракт).

При несоответствии — **алерт (лог ERROR + событие в окно) и блок ВХОДОВ** (skip
с причиной `wrong_chart`); открытая позиция продолжает вестись/закрываться штатно.
Когда график снова совпадает — блок снимается автоматически. Актуально для
paper/live, не для бэктеста.

Отдельно: если по `chart_tag` **вообще нет свечей** (тег переименован или график
с этим тегом не открыт в QUIK), робот не получает данных, `handle_bar` не
вызывается — и охрана контракта тут бессильна. Этот случай ловится отдельно: на
старте и в цикле, если `get_candles` по тегу пуст, робот пишет ERROR «нет свечей
по тегу» и шлёт событие в окно (при восстановлении данных — сообщение в лог).

## Восстановление позиции при рестарте (adopt_live_position)

При старте LIVE робот не только реконструирует диапазон/флаги реплеем сегодняшних
баров, но и **сверяет позицию с фактической в QUIK** (`read_position_detail`) и
приводит состояние к реальности:

- QUIK плоско, реконструкции нет — норма;
- QUIK плоско, а по барам была позиция — она закрылась, пока робот был offline:
  состояние сбрасывается в плоское, сторона помечается использованной (не
  переоткроем сегодня) + алерт;
- в QUIK есть позиция — **подхватывается**: сторона/размер из позиции, стоп из
  активной стоп-заявки (`active_stop_price`), цена входа из средней цены позиции;
  если позиция «неожиданная» (реконструкция по барам её не дала) или не найдена
  стоп-заявка — громкий алерт «сверь вручную».

Работает в live при `execution.verify: true`; в paper/verify-off — прежнее
поведение (предупреждение в лог, без автоподхвата). Как и остальная сверка,
зависит от `get_futures_holding`/`get_stop_orders` в твоей версии QuikPy.

## Сайзинг позиции (sizing, пункт №4)

Размер позиции = `min(риск-лимит, ГО-лимит)`, где входы (стоимость пункта и ГО на
контракт) читаются из QUIK. Живые чтения бывают «мусорными» (0, спайк), и один
такой на входе открыл бы позицию неверного размера. Защита (секция `sizing`):

- **ГО** вне `[go_min_rub, go_max_rub]` (по умолчанию 3000..100000) или не прочитано
  → берётся `backtest.go_per_contract_assumed` + предупреждение в лог;
- **стоимость пункта** ≤ 0 → 1.0;
- база капитала: по умолчанию `deposit_rub`; при `from_live_equity: true` — живой
  equity из QUIK (по сути компаундинг), с фолбэком на `deposit_rub`, если equity не
  прочитан или подозрительно мал (`equity_min_rub`);
- **риск-лимиты** (дневной/недельный) всегда считаются от `deposit_rub` —
  фиксированная точка отсчёта потерь, не зависящая от чтений.

Каждый вход логируется с параметрами сайзинга (`капитал/ГО/rpp/стоп`) — размер
позиции всегда можно сверить по логу. NB: при рестарте в live размер берётся не
из этого расчёта, а из ФАКТИЧЕСКОЙ позиции QUIK (см. восстановление выше).

## Известные ограничения

- Восстановление позиции требует, чтобы QuikPy отдавал `get_futures_holding`
  (позиция) и `get_stop_orders` (стоп); если методов нет — робот предупредит и
  оставит реконструкцию по барам, контролируй вручную.
- Точное время входа подхваченной позиции неизвестно (в QUIK его нет) — в журнале
  ставится время рестарта; на логику EOD/стопа это не влияет.
- `entry`/`exit` в журнале для paper/live — цена close/open сигнального бара,
  не фактическая цена исполнения от брокера (в бэктесте это скорректировано
  на slippage, в paper/live для точной цены нужно читать подтверждение сделки
  из QUIK — возможное дальнейшее улучшение).
- Контракт для M15-графика в QUIK переключается ПОЛЬЗОВАТЕЛЕМ вручную по
  подсказке в логе — робот не может сам открыть/переключить график в терминале.
